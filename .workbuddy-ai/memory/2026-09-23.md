# 2026-09-23 — Responsive UI bug fixes (portfolio site)

Task: fix responsive-only UI bugs in the React/Vite/Tailwind v4 portfolio, with the
About page called out as the example.

## Layout system (important convention)
Public pages share a fixed two-column shell: a `w-14` (56px) SnakeBar rail + a sidebar
nav, whose total width is meant to line up with the header's brand column so the header's
vertical divider continues down through the page.
- `xl` (1280px)+ : brand `513px` = rail 56 + sidebar `457px`
- `lg` (1024px)  : brand `400px` = rail 56 + sidebar `344px`

If you change the header brand width you MUST change the sidebar width in
`About/SubjectBox`, `Project/FilterBox`, `Blog/index`, `Blog/Post`, `Contact/ContactBox`
to keep them aligned.

## Bugs found (via puppeteer audit, not guessing)
1. **Collapsed mobile menu painted a bordered empty strip.** `.mobile-nav-panel` collapses
   with `max-height:0; overflow:hidden` but kept `border-t` + `border-b`, so it rendered a
   2px-tall bordered box at `top-[55px]`, stacked on the header's own 1px bottom border →
   a ~3px "double border with an empty gap" under the header on every page. This was the
   exact thing the user described.
2. **Header nav broken from 768–957px.** Desktop nav switched on at `md` (768px) but needed
   ~958px (513 brand + 314 links + 131 contact) → `_Contact-me` overlapped `_Project`/`_Blog`
   and `scrollWidth` was 827 > 768.
3. **About sidebar double borders.** The `contacts` h2 had `border-t` which collided with the
   bottom border of whatever sat above it: (a) mobile with `personal-info` collapsed;
   (b) desktop with the `skills` tab active.
4. **Split layouts switched on too early (768px).** About content pane was crushed to 255px
   (text wrapped one word per line, Skills 2-col grid unusable). Same for Project/Blog/Contact.
5. **Footer label wrapped at 320px** ("find-me-in :" broke onto two lines, footer 72px tall).

## Fourth change — Home hero typing animation freeze (deterministic fix)
Symptom reported by the user: on the home page the name with the typing animation sometimes
never appears / locks part-way, and only a refresh fixes it.

Reproduced deterministically, 12/12 runs: intro stopped at `"Hi all|"`, name empty, role never
rendered. Root cause was `typeit-react` under React StrictMode:
- its init effect ends with `instanceRef.current?.updateOptions(opts) || generateNewInstance()`.
  `updateOptions()` returns the instance (always truthy), so the rebuild branch only runs while
  the ref is null. StrictMode mounts → cleanup (`destroy()`, ref still pointing at the dead
  instance) → remounts, reusing the destroyed instance → nothing types, `afterComplete` never
  fires, the whole sequence stalls.
- Using the TypeIt core directly also failed (12/12, with DOUBLED characters — `"MMoohhaamm…"`)
  because the core's `#fire()` loop is `requestAnimationFrame`-driven with no `destroyed`
  guard; `destroy()` only clears `setTimeout` ids, so the StrictMode cycle left a second live
  loop writing into the same element.

Fix: new `src/Components/Typewriter/index.jsx` with **no TypeIt dependency at all** — its own
`setTimeout` chain, one writer per mount, cleanup cancels the timer and clears `textContent`.
API `text / as / speed / lifeLike / cursor / onDone`. `InformationText` now uses it for all
three hero lines. Caret is a `<span class="ti-cursor">` whose `|` comes from CSS `::before`
(added to `index.css`), so `textContent` stays exactly the prop text — the caret is invisible to
copy/paste, screen readers and tests. `typeit-react` was then uninstalled from `package.json`
(no imports remained; bundle was already tree-shaken, so size was unchanged).

Verified: 12/12 cold loads OK, 8/8 remounts after client-side navigation OK (0 console errors),
and 6/6 widths (360/390/768/1024/1280/1920) OK with no horizontal scroll.

## Fifth change — Contact code pane overflow, properly fixed

line break into a sideways scroll. Measuring the real line boxes (not `scrollWidth`, which
clamps to `clientWidth` and always reports "fits") showed the longest line needs 458px of
content while the pane offers ~372px at 1280 — a 94px spill.

Replaced the flat `<p>`+`<br>` markup with one flex row per line: a fixed-width line-number
gutter span + a `min-w-0 whitespace-pre-wrap break-words` code cell, driven by a `[text, color]`

- 320–1920px: 0 spill (13px slack on mobile, 24px on desktop), no scrollbar in the pane
- the longest line wraps INSIDE the code cell, so the continuation aligns under the code
  instead of under the line number
- at 1600px+ nothing wraps at all, so the desktop look is unchanged
Added a stable `.code-preview` class on the pane for auditing.

## Audit-harness fix (important, do not lose this)
Adding the full-screen panel broke the audit with **55 NAV-OVERLAP and 110 spill flags on every
route** — all false. Cause: the panel's rows are `fixed`, so they keep non-zero
`getBoundingClientRect()`s even while `visibility: hidden`, and `audit.mjs` only filtered on
rect size. The panel's re-drawn brand row sits exactly on top of the header's own brand link,
which is what produced the "overlaps".
Fix: `audit.mjs` now skips any element whose computed `display`/`visibility`/`content-visibility`
marks it unrendered. Because `visibility` is inherited, that one test excludes the whole closed
overlay. Lesson: **a rect-based audit must filter on rendered-ness, not just on rect size.**

Also note: `page.evaluate(() => sessionStorage.setItem("booted","1"))` after `goto` is TOO LATE —
`App` reads that flag during its first render, so the loader still mounts for its 600ms minimum
and swallows the first synthetic click. Use `page.evaluateOnNewDocument(...)` before `goto`.

Final state after this change: `npm run build` passes; `audit.mjs` over 5 routes × 16 widths
gives 0 H-SCROLL, 0 NAV-OVERLAP, 0 PANEL-ARTIFACT, 0 non-blob spills (the 16 remaining
`OVERFLOW` flags are the documented decorative glow blobs on /project and /blog); typing still
0/12 failures.

## Seventh change — replaced both blog posts
The user asked to delete their two posts and add two new ones of my choosing.

**Where the blog lives:** `public/api/blog.json` is the single source of truth. Both the dev mock
plugin (`vite-plugin-mock-api.js`) and the production handler (`api/_blog.js`) read that file via
`_data.js` → `BUNDLED["blog.json"]`. The `readStore` overlay lives in `/tmp/portfolio-data`
(`DATA_DIR`, ephemeral per instance) and only exists if the admin panel has written to it — it
did not, so the bundled file was live.

**Content format** (`parseBlocks` in `src/lib/blog.js`): blocks split on `/\n{2,}/` first, so
each block must be its own blank-line-separated chunk. A chunk of only `- item` lines becomes a
`ul`, only `1. item` lines an `ol`, `## text` an `h` (these also feed the post's outline sidebar),
`> text` a quote callout, everything else a paragraph. **The renderer does no inline markdown** —
backticks and asterisks would print literally, so code identifiers are written as plain words.
I generated the file with a throwaway node script (arrays of blocks joined with `\n\n`) rather
than hand-writing JSON with embedded escapes.

**The trap I fell into (worth remembering):** I reused the same `join("\n\n")` helper for the
lines *inside* a list, so every bullet became its own one-item list — 9 lists instead of 3. It is
a silent failure: the page still renders bullets, just with `my-2` + `gap-2.5` between every
single item instead of between groups, so it only shows up as slightly wrong spacing. Detect it by
asserting on the **item counts** (`[3,2,4]`), not just "a list exists". The generator now has a
self-check that aborts if any list block has exactly one item. Generalised: when a format is
delimited by blank lines, use a *different* joiner for inner lines than for outer blocks.

**Deleted:** `welcome-to-my-blog`, `why-i-rebuilt-my-portfolio`. Both are still in git history
(`git show HEAD:public/api/blog.json`).

React filler, since concrete debugging stories are what actually demonstrate competence on a
portfolio:
- `stop-guessing-at-responsive-bugs` — "Stop guessing at responsive bugs. Measure them."
  (2026-09-23, tags CSS/Debugging/Frontend, 868 words, 9 headings). The border-ownership bug,

## Ninth change — admin analytics: view counting + persistence

User asked: "if a user opens 4 pages it should record 4 views, the total should increment per
page, and below each page should get 1 — and it must stop resetting, the data should be saved."

### Root cause 1 — every page view was counted TWICE
Reproduced with a real browser (`tools/probe-visit-counting.mjs`, puppeteer-core + system
Chrome, counts POSTs to /api/admin/track on the wire):
- 4 hard page loads -> **8** views (wire=8, stored=8)
- 1 load + 3 SPA navigations -> **5** views (only the first page doubled)

Signature = React StrictMode double-invoking the mount effect (setup -> cleanup -> setup).
Note `AbortController.abort()` in the cleanup does NOT un-send the request — Chrome had already
dispatched it, which is why both calls reached the server. My first theory (that abort would
cancel the in-flight request) was wrong; the measurement is what settled it.

Fix in `src/Components/VisitTracker/index.jsx`: a `lastCountedRef` guard keyed on
`location.pathname`. The ref survives StrictMode's effect teardown (same component instance), so
the second setup is a no-op. Replaced the AbortController with `keepalive: true` — a
fire-and-forget beacon must never be cancellable. Also extracted an `isAdmin()` helper, which
removed two pre-existing empty `catch {}` blocks (2 eslint `no-empty` errors).

Verified after the fix: 4 hard loads -> 4, 1 load + 3 SPA -> 4, revisit "/"->"/about"->"/" -> 3
(a genuine revisit still counts — the guard is not over-deduping). `total == sum(paths)` always.

### Root cause 2 — three separate storage roots, one of them ephemeral
| backend | storage | durable? |
|---|---|---|
| `npm run dev` (vite mock plugin) | `public/api/admin/data/*.json` | yes (real disk) |
| `npm start` (`server.js`) | `data/*.json` | yes |
| Vercel (`api/`) | `/tmp/portfolio-data` | **NO — wiped per cold start** |

Correction to an earlier note: `public/api/admin/data/` is NOT git-tracked — the `data/` rule in
`.gitignore` (line 31) matches it at any depth. It is local-only, which is fine.

Fix: added a durable store layer to `api/_lib.js`. When `KV_REST_API_URL` + `KV_REST_API_TOKEN`
(or the Upstash-named pair) are set, Redis-REST becomes the source of truth; otherwise it behaves
exactly as before (files). All 40 `readStore`/`writeStore` call sites already `await`, so this
was a **drop-in swap with zero call-site changes**. Added `deleteStore()` and rewired
`api/admin/_reset.js` + `resetSabzData()` to use it — a plain `fsp.unlink` would have left the
durable copy behind, so the reset button would not actually wipe anything.

Also exposed `storage`/`durable` in the stats payload and added a **saved / not saved** badge next
to "live" in the admin analytics header, so an ephemeral host is never a silent surprise again.

### Verification tooling (new, all in tools/)
- `probe-visit-counting.mjs` — drives real Chrome, counts track POSTs on the wire, 3 scenarios.
- `verify-durable-analytics.mjs` — runs a fake Upstash-REST server in-process, records 4 views,
  **deletes the instance's /tmp**, then reads from a brand-new data dir. Includes a control run
  with no KV (must reset to 0) — without that control the test could pass for the wrong reason.
- `verify-store-endpoints.mjs` — sweeps all 12 store-backed endpoints on both the file store and
  the durable store, requiring identical well-formed answers.
- `shot-admin-analytics.mjs` — screenshots the panel (temporarily writes a local admin config and
  always restores it, since dev login is credential-less by design).

Gotcha: the fake KV server must live in the PARENT process, so the child must be spawned with
`spawn` (async), NOT `spawnSync` — `spawnSync` blocks the parent's event loop and the child's HTTP
call can never be answered, so every durable write silently times out and the test "fails".

### Also fixed — dev/prod day-key mismatch
The vite mock keyed days with `toISOString()` (UTC) while `api/_lib.js` uses local dates. Iran is
UTC+3:30, so a visit between 00:00 and 03:30 local was filed under the *previous* day in dev and
the current day in production. Replaced all 6 UTC sites with a local `dstr()` matching `_lib.js`.
Also made the demo seed derive `total` from its `paths` so seeded days satisfy
`total === sum(paths)` — they used to sum short of their own total, which reads as a counting bug.

### State
`npm run build` passes. eslint clean on every file I touched except the 11 pre-existing
`no-undef` errors in `vite-plugin-mock-api.js`. Endpoints: 12/12 on both stores. Counting: 3/3
scenarios. Durable: survives simulated cold start, control resets to 0.

Open item for the user: to make the LIVE Vercel site durable they must provision Upstash/Vercel KV
and set the two env vars. Nothing breaks without them (file fallback), but the deployed site will

## Tenth change — full-project bug audit (user: "کل پروژه رو چک کن ببین باگهاش چی میتونه باشه")

Method: whole-project eslint, a delegated deep read of all three backends + React app, then I
personally verified every high-severity claim by reading the code AND reproducing it at runtime
against the real `api/index.js` handler. New tool `tools/verify-security.mjs` is now the
regression suite for these (4 checks, all PASS).

### FIXED — confirmed and verified

1. **`api/admin/_fs.js` — `POST fs-delete {path:""}` wiped the entire data directory.**
   `safeJoin("")` resolves to DATA_DIR and the containment check PASSES (the root IS inside the
   root), so `fsp.rm(DATA_DIR, {recursive:true})` deleted messages, visits, clicks, the blog
   overlay AND admin-auth.json. `server.js:1775` and the mock (`vite-plugin-mock-api.js:1717`)
   both had an `if (!rel) refuse` guard — the serverless copy was missing it. Runtime-proved:
   2 files -> 0 files, `{"ok":true,"deleted":""}`.
   ⚠️ My first fix put the guard BEFORE the method check, which also blocked the legitimate GET
   listing of the root (the Database page) — my own test caught it (`before: []`). The guard is
   now scoped to the POST branch only, and the test asserts the root is still listable.

2. **`api/index.js` + `api/_skills.js` — admin edits never reached the live site.**
   `_projects-admin`/`_skills-admin`/`_blog-admin` write to an overlay via `saveData`, and the
   panel reads it back via `listData`, but the PUBLIC routes read `BUNDLED` (the git-tracked file)
   directly: `STATIC_JSON["projects.json"]` etc. and `_skills.js`. So adding a project or skill
   appeared to save in the panel and never showed on the site. `/api/blog` was already correct
   (it uses `listData`). Fixed by routing STATIC_JSON + `_skills.js` through `listData` (which
   falls back to BUNDLED, so behaviour is unchanged when no overlay exists). Verified: create in
   the panel -> appears in `GET /api/projects.json` and `GET /api/skills`.

3. **`api/_lib.js` — a password change did not invalidate existing tokens.**
   `saveAdminPassword` set `token_version: cur.token_version || 0` (unchanged), and `tokenSecret()`
   derives from deploy-time env / the baked-in default, NOT from the stored password — so old
   tokens kept verifying, directly contradicting `_password.js`'s own header comment. Now bumps
   `token_version`. Verified: old token 401, freshly issued token 200.

4. **`src/Hooks/useClickTrack.js` — clicks were being aborted and lost.**
   Same anti-pattern as the VisitTracker bug fixed earlier: every new click called
   `abortRef.current.abort()` on the previous in-flight beacon. The throttle only de-dupes the
   SAME target, so clicking A then B within one round-trip cancelled A. Real events never reached
   the server. Replaced with `keepalive: true` (and dropped the now-unused `useRef`).

5. **`vite-plugin-mock-api.js` — unknown blog slug threw and returned HTML.**
   The handler called `res.writeHead(200, ...)` unconditionally, then `writeHead(404, ...)` for a
   missing slug -> `ERR_HTTP_HEADERS_SENT` ("Cannot write headers after they are sent to the
   client"). Vite answered with its own HTML error page, so the app did `JSON.parse("<!DOCTYPE")`
   and the user saw `Failed to execute 'json' on 'Response': Unexpected token '<'`.
   Status is now set inside each branch. (Found only because `probe-routes.mjs` flagged
   `/blog/welcome-to-my-blog` as BLANK on mobile — a slug I had deleted in an earlier session, so
   the probe was stale too; its ROUTES now use a live slug.)

6. **`src/Page/Blog/Post/index.jsx` — raw parse error shown to the user.**
   `await postRes.json()` ran BEFORE the status check, so any non-JSON body surfaced the raw
   syntax error. Now parses defensively and reports a clean "Post not found".

### REPORTED, deliberately NOT changed

- **`api/_sabz.js` returns every account's PLAINTEXT password on a PUBLIC endpoint.**
  Confirmed at runtime (unauthenticated GET returns `password: "SuperSecret123!"`). It looks like
  a typo (`({password, ...rest}) => ({...rest, password})`) but it is LOAD-BEARING: the prebuilt
  Sabz-Learn bundle does the whole login in the browser
  (`users.find(u => u.phoneNumber === phone)`, then `user.password == typedPassword`, then it
  invents a token with `crypto.randomUUID()`). Removing the field breaks that login and
  `all/dist` ships with no `src/` in this repo, so the client cannot be rebuilt from here.
