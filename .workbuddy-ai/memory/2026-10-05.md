## Admin panel persistence → Supabase/Postgres

**Problem reported:** nothing in the admin panel saved — telegram bot token, site
info, project layout/order, skills, and messages all reverted. Root cause was
`api/_lib.js` storing everything under `DATA_DIR = /tmp/portfolio-data`, which is
**per-instance and wiped on every cold start** on Vercel. Two lambdas also did
read-modify-write on the same whole-file blob, so one save could silently drop
another. `NODE-BACKEND.md` claimed a Redis/KV store that was **never implemented**
(no code referenced `KV_REST_API_*`), which is why the panel looked "durable".

**Fix — new default DB backend:**
- `api/_pg.js` (new) — `postgres.js` client + typed helpers:
  `kvGet/kvSet` (admin_settings JSONB rows), `pgListProjects/pgReplaceProjects`,
  `pgListSkills/pgReplaceSkills`, `pgListMessages/pgInsertMessage/pgSetMessageStatus/pgDeleteMessage`.
  Reads `SUPABASE_DB_URL` ∥ `DATABASE_URL` ∥ `POSTGRES_URL`. Auto-sets
  `prepare:false` when the URL contains `pgbouncer=true`.
- `api/_lib.js` — `readStore`/`writeStore` are now **DB-first with /tmp fallback**.
  Each panel document is ONE `admin_settings` row keyed by filename
  (`telegram.json`, `site.json`, …); `key` is PRIMARY KEY so concurrent lambdas
  can't clobber each other. `storeBackend()`/`storeDurable()` report the truth;
  admin password (`admin_auth` key) also persists now.
- `api/admin/_skills-admin.js`, `_projects-admin.js`, `_messages.js` — use the
  relational tables when a DB is configured, JSON store otherwise.
- `sql/006_supabase_panel_store.sql` (new) — single idempotent file: tables
  `admin_settings` / `projects` / `skills` / `contact_messages`, RLS (anon can
  read published only; `admin_settings` is fully closed), seeds from the existing
  JSON.
- `src/Page/Admin/Site/index.jsx` — warning text updated to Supabase.
- `NODE-BACKEND.md` — replaced the fictional Redis section.
- Added `postgres` dependency.

**Verification (important):** Docker/WSL are blocked in this sandbox, so DB tests
used **PGlite** (real Postgres in WASM) + `@electric-sql/pglite-socket`, which
exposes a real TCP port — the genuine `postgres.js` client from `api/_pg.js`
connected unmodified. Verified: migration idempotent (7 skills / 8 web / 2 mini,
stable on re-run), telegram token round-trip, **key-collision isolation**
(saving site no longer wipes telegram), project reorder persistence, skills
replace, message insert/status/delete ordering, `storeBackend()` →
`supabase-postgres` / `durable:true`. Also verified all admin HTTP endpoints on
port 3199 against `server.js`.

**Gotcha found & fixed:** the first migration draft used `ON CONFLICT DO NOTHING`
on `skills`/`projects`, which has **no conflict target with no unique key** — a
second run duplicated every row (14 skills, 16 projects). Replaced with
`INSERT ... SELECT ... FROM (VALUES ...) AS v(...) WHERE NOT EXISTS (...)`.

**Still requires the user (one-time):** run `sql/006_supabase_panel_store.sql` in
Supabase SQL Editor, then set `SUPABASE_DB_URL` (transaction-pooler URI, port
6543) in Vercel env vars and redeploy. Nothing else.

## Typewriter jitter on the Home hero name

User reported "sometimes the name glitches while typing". Root cause was the
component reaching into the DOM with refs on every keystroke:
- `paint()` did `el.textContent = text.slice(0, shown)` then
  `el.appendChild(newCaretSpan)` — that destroyed and recreated the caret
  element on every character, so the `tiBlink 0.8s` animation restarted
  from frame 0 every ~50–78 ms. Result: the cursor flickered instead of
  smoothly blinking, and on the 21-char name the jitter was visible for
  almost a full second.
- Doing the same imperative dance on each keystroke also fought React's
  render cycle — StrictMode's deliberate dev-mode double-invoke could
  leave a stray character on screen for a frame, and HMR / Fast Refresh
  could desync the typed cursor from the element.

Rewrite: `src/Components/Typewriter/index.jsx`
- `shown` is now `useState`, the text is rendered as `{text.slice(0, shown)}`
  through the normal JSX path — no `ref`, no `textContent`, no
  `appendChild`. React owns the DOM, the caret effect is direct.
- Caret is a stable sibling `<span className="ti-cursor" aria-hidden>`
  inside the same `<As>`. The element is created once, the blink animation
  runs uninterrupted for the whole typing run.
- `useEffect` for scheduling is unchanged in shape (random `speed * 0.6–1.4`
  per char) but its cleanup always `clearTimeout`s, so StrictMode's
  double-invocation cancels the first timer and only one chain of
  characters is ever queued.
- Existing call sites (`InformationText` for `Hi all. I am`, the name, and
  `> Front-end developer`) work unchanged: `text`, `speed`, `cursor`,
  `onDone`, `as`, `lifeLike`, `...rest` all keep their semantics. The third
  line's caret still blinks after typing (same as before, since
  InformationText passes `cursor={true}` for it).
- Verified `vite build` compiles clean.
